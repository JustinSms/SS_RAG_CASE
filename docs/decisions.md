# Decision log

Running log: choice, rejected option, why. Also records what broke. Feeds the README ("decisions and why") and the Q&A in the call.
Seeded from the planning phase, 2026-10-03.

## Key decision: retrieval is evaluated by source overlap only; the answers are not evaluated yet

**Decision.** The evaluation (`eval/`) measures only the overlap between the sources the system retrieves and the gold sources (document and heading) for each question, as **accuracy, precision and recall**. It does not generate answers and does not grade them.

**Why.** It is a quick win: no hand grading (about an hour for 120 answers), no LLM judge to defend, deterministic and cheap, and it still shows whether the right passages are found, which is the part the pipeline controls.

**What this does not tell us.** Good source overlap is necessary for a good answer but not sufficient: the model can still misread, ignore or over-extend the context. Citation validity and precision are also not measured here.

**Next step (must be done).** Evaluate the actual answers, by hand (correct / partial / wrong against a reference answer) or with an LLM judge, together with citation validity and precision. Add `reference_answer` to the question files at that point. The README and the call must say clearly that answer quality is not yet measured.

**Rejected for now.** Hand grading of all answers (too slow for the first pass); LLM judge (one more thing to defend, and it needs validating against hand grades first).

## Other decisions

Agreed in the design (reasons in `design/tech-stack.md` and `design/app-structure.md`), then the choices made per milestone:

- Own frontend and backend; old `rag/` code not reused, only ideas.
- Local bge-m3 and bge-reranker-v2-m3 instead of paid services: one API key for reviewers. Rejected: Voyage.
- One Haiku call per section for enrichment. Rejected: one call per chunk (slow), Message Batches API (asynchronous, breaks a live upload).
- Postgres + pgvector. Rejected: Chroma/LanceDB/Qdrant.
- FastAPI + React, SSE for streaming. Rejected: Next.js API routes, Streamlit/Gradio, WebSockets, Celery/Redis.
- Neighbours vs. LLM section selection comparison: out of scope, a next step.
- Optional steps (rewrite, rerank, section selection, enrichment) fall back instead of failing; only the answer call is required.
- `SIMILARITY_CUTOFF` default 0.45 (lowered from 0.70): bge-m3 cosine scores for relevant passages often sit around 0.5-0.7, so the cutoff only removes clear noise and the reranker does the real filtering. Tuned in the evaluation.
- Dense search only in v1. Next step: keyword search (BM25 via Postgres full-text search) as a hybrid, compared in the evaluation. Rejected for now: one more retrieval path to tune before the happy path works.
- No OCR in v1; scanned PDFs are rejected as "no text found". Next step: OCR for pages without a text layer (for example Tesseract via PyMuPDF).
- `/api/health` always returns 200 while the app is up; the body carries `healthy` and a `problems` list (`level` error or warning). A non-200 would make the `api` container unhealthy, and then `web` (which waits for it) could never start and show the setup banner. The compose healthcheck therefore only proves the app answers.
- API key check: one `models.list(limit=1)` call at startup through `llm/client.py`, result cached until restart. Rejected: a tiny message call (costs tokens, needs a prompt). Auth errors mean "invalid", other API errors mean "unreachable".
- Memory check reads `MemTotal` from `/proc/meminfo` (the Docker VM), not available memory, which fluctuates. Skipped when the file does not exist.
- `RERANK_MIN_SCORE` defaults to `None` until it is tuned in milestone 8. `ANTHROPIC_API_KEY` defaults to empty so a missing key shows up in health instead of crashing at startup.
- Backend image: build context is the repo root (so `env/` can be copied in), `uv sync --frozen` from `uv.lock`, pinned `python:3.11.15-slim` and `uv:0.10.12`. `env/.env` is kept out of the image by `.dockerignore`; compose passes it in with `env_file` (optional, so a missing file shows the missing-key problem).
- Frontend toolchain: exact-pinned versions in `package.json` plus `package-lock.json`; TypeScript 6.0.3, not 7. `typescript-eslint` 8.71 only supports TypeScript below 6.1, and lint matters more than the newest compiler. Move to 7 when `typescript-eslint` supports it.
- shadcn components are added with the CLI and then edited: the CLI v4 wrote `import { cn } from "cn"` and added an unrelated npm package `cn` plus the `radix-ui` umbrella. Replaced by `@/lib/utils` and `@radix-ui/react-slot`, both pinned.
- Frontend tests use vitest + Testing Library with `fetch` stubbed (no network, no api needed). `npm test`.
- The browser polls `/api/health` every 5 s (`HEALTH_POLL_MS`), so the banner clears after the user fixes the key and restarts the api, without a reload. An unreachable api shows the same red banner.
- `web` serves on 8080 (nginx container port 80); the `api` port 8000 is no longer published. For `npm run dev`, publish it again or run uvicorn locally (vite proxies `/api` to `localhost:8000`).
- nginx 10m limit duplicates `MAX_UPLOAD_MB` (nginx cannot read pydantic settings); noted in `nginx.conf`. Base images pinned: `node:24.14.1-alpine`, `nginx:1.30.0-alpine`.
- Upload checks run on all files of a request before any is stored; one bad file rejects the request. A `409` carries the existing document as `document` in the body (a file repeated inside one request gets `409` with `document: null`). PDFs are opened with PyMuPDF to detect encryption; a file PyMuPDF cannot open is `415`. Order of checks: size (`413`), header (`415`), readable/encrypted (`415`).
- Files are stored as `UPLOADS_DIR/<document id>.pdf`; the original name lives only in the database, so odd file names never touch the file system.
- Queue: one daemon worker thread over `queue.Queue`. A crash in the pipeline marks that document `failed` with the error and the worker carries on with the next one.
- Unit tests use in-memory SQLite, not Postgres: `Vector` and `ARRAY` columns have JSON variants for SQLite (in `db/models.py`) and the HNSW index is Postgres-only. Cascade, the pgvector extension and the index were checked by hand against the real `db` container. Rejected: tests that need the `db` container (pytest would then not run on a laptop without Docker).
- `pgvector`, `python-multipart` and `pymupdf` added to the backend (pinned by `uv.lock`); PyMuPDF is reused for parsing in milestone 4.
- Chunk sizes use a token estimate (`ceil(characters / CHARS_PER_TOKEN)`, default 4), not the bge-m3 tokenizer. It needs no model download, so tests and parsing run offline. English text is close to 4 characters per token, German and tables use more tokens, so real chunks can be somewhat above the estimate; `MAX_CHUNK_SIZE` (about two pages) has room for that. Rejected: loading the tokenizer in ingestion (needs the model, slows the tests).
- `pymupdf4llm` pulls in `pymupdf-layout` (with onnxruntime, numpy) for its heading detection. Accepted: it is pinned by `uv.lock` and gives better headings than the plain version.
- Sections: heading level = number of `#`. A skipped level (`#` then `###`) attaches to the nearest shallower heading. Headings without text stay as empty sections (no chunks), so the tree matches the table of contents. Text before the first heading goes into a root section called "Start of document". A PDF with no headings at all becomes "Part 1", "Part 2", ... of about `MAX_CHUNK_SIZE` tokens.
- Chunker: the overlap is the last `CHUNK_OVERLAP_TOKENS` of the previous chunk, cut at a word boundary, so a chunk holds at most `MAX_CHUNK_SIZE - CHUNK_OVERLAP_TOKENS` tokens of new text. A paragraph longer than that is cut at word boundaries. A page break inside a paragraph (PyMuPDF4LLM works per page) splits it into two paragraphs, one per page.
- Milestone 4: documents become `ready` after chunking, although nothing is embedded yet. They cannot be searched until milestone 6.
- Milestone 5: the dropzone limit is a constant (`MAX_UPLOAD_MB = 10` in `frontend/src/lib/upload.ts`), the third copy of the limit next to `env/config.py` and nginx. Files that fail the browser check are skipped and the valid ones in the same drop are still uploaded (the backend would reject the whole request). The list polls only while a document is `processing`. The progress bar is left out until a later milestone, as the plan says.
- Milestone 6: embeddings use `sentence-transformers` with `torch`; on Linux uv takes the CPU-only wheel from the PyTorch index (no CUDA packages in `uv.lock`), on macOS the default wheel. bge-m3 is pinned by commit (`EMBED_MODEL_REVISION`) and downloaded in the Dockerfile by `backend/download_models.py`, which reads `env/config.py`; only the files sentence-transformers needs are fetched (no ONNX copies). Changing `env/config.py` re-runs that layer and downloads the model again. Accepted: one source for the model name. `HF_HUB_OFFLINE=1` is set after the download.
- Milestone 6: vectors are normalised, so similarity = 1 - cosine distance. The model loads at api startup (before the app accepts requests); `/api/health` reports `model_not_loaded` as an error otherwise.
- Milestone 6: search takes the closest `MAX_CANDIDATES` chunks of `ready` documents, logs the best scores before the cutoff (so a question with no hit still shows its scores), then applies `SIMILARITY_CUTOFF`. The pipeline keeps the first `TOP_N` and sorts them by (file name, document, position) for the context. `search_chunks` uses pgvector SQL and is not unit tested on SQLite; tests replace it with a fake, and it was run against the real `db` by the smoke test.
- Milestone 6: chunk labels (`c1`, `c2`, ...) are numbered per question in document order, not stored. `/api/chat` returns `sources` for every chunk in the context, and the frontend shows only the ones the answer cites. Earlier answers sent back as history have their `[cN]` removed, because the numbers belong to the question they were answered for. A failed answer call is a `502` with a message.
- Milestone 6: the UI keeps the chat in React state only. Errors appear as a message in the list and are left out of the history sent with the next question.
- Milestone 7: enrichment is one Haiku call per section (per `ENRICH_BATCH_SIZE` chunks for long sections). The document is the first content block with `cache_control`, the chunks are the second, so the cache is hit by every call. The first section runs alone to write the cache; the rest then run `ENRICH_CONCURRENCY` at a time. Accepted: one extra step of waiting at the start. Rejected: starting all calls at once (each would pay for the document, because the cache is only readable once the first reply starts).
- Milestone 7: a reply is valid only if it holds exactly one entry with string `context`/`summary` and a list of string `keywords` for every chunk id given (ids are 0..n-1 within the call, not database ids). A ```json fence around the reply is stripped. Any failure (bad JSON, missing ids, API error after the SDK retries) is retried `ENRICH_RETRIES` (1) time, then the group is stored with `enriched = false` and embedded as plain text.
- Milestone 7: worker threads only call Anthropic; the pipeline thread writes to the database, so one SQLAlchemy session is never shared. `chunks_done` is committed as each section finishes, in completion order. Chunks are committed (without embeddings) before enrichment starts so `chunk_count` is known for the progress bar; the document stays `processing` until the embeddings are stored.
- Milestone 7: when the document is over `ENRICH_DOC_MAX_TOKENS` (150K by the same character estimate as chunk sizes, below Haiku's 200K window to leave room for the chunks and the reply), the call gets the section text instead of the document.
- Milestone 7: the tests replace `enricher.complete` with a function that raises (autouse), so no test reaches the network; tests that need replies install their own fake.
- Milestone 8: the reranker is `CrossEncoder` from sentence-transformers with a sigmoid, so scores are 0-1 and `RERANK_MIN_SCORE` is a plain number. bge-reranker-v2-m3 is pinned by commit (`RERANK_MODEL_REVISION`) and downloaded next to bge-m3 in `download_models.py` (only the `model.safetensors` and tokenizer files). It loads at api startup, but unlike the embedder a failed load is only logged: reranking is optional, so health does not report it and questions use the cosine order. Added `RERANK_BATCH_SIZE` (8) and `RERANK_MAX_LENGTH` (2048).
- Milestone 8: `RERANK_MIN_SCORE` is now a float, provisional default 0.1 (was `None`). On a 2-page test PDF the right chunk scored 0.96-0.995 and the unrelated one 0.01; the two unanswerable questions I tried were already stopped by the cosine cutoff (best cosine 0.22-0.29), so the rerank threshold was not exercised on real unanswerable questions. Tune it in the evaluation. Known weak spot: an English question against a German passage scored 0.013 in a quick check, so cross-language questions can be refused at 0.1; the evaluation has the English/German pair to measure this.
- Milestone 8: the reranker scores the chunk text only (not the context sentence). When the reranker fails there is no score, so the `RERANK_MIN_SCORE` check is skipped and the top N by cosine are used. Rejected: treating a failed reranker as "not found" (breaks the fallback rule).
- Milestone 8: `select_context` returns the context and a `Trace` (candidate ids after the cutoff, ids after reranking or `None`, the top N ids, best rerank score, `not_found`). `ChatResult` carries it; `/api/chat` does not send it to the browser. With 2 pages of text the api container idles at about 1.1 GiB with both models loaded, well inside 8 GB; the peak during a large rerank was not measured.
- Milestone 9: the rewrite runs only when there is history (nothing to resolve otherwise). The rewritten question is used for the embedding, the reranker and the selector; the answer call still gets the user's own words plus the history. The trace keeps it as `search_question`. Rewrite uses `REWRITE_MODEL` (Haiku); selection uses `SELECT_MODEL` (Sonnet), both new settings.
- Milestone 9: the selector numbers the chunks of the kept sections 1..n in the prompt (not UUIDs or `cNN` labels, which only exist after combining) and marks the top N chunks as "kept". It replies `{"chunks": [3, 7]}`. Unknown, kept and duplicate numbers are ignored; invalid JSON or a failed call (also a failed section load) adds nothing and is not retried. Rejected: a retry like enrichment has, since the answer is still good from the top N and the call is on the user's waiting path.
- Milestone 9: added `MAX_SELECTED` (10) to cap the extra chunks, so one broad section cannot blow up the answer context, and `SELECT_FALLBACK_CHARS` (300): a chunk without a summary (unenriched) shows the start of its text to the selector. The call is skipped when every chunk of the kept sections is already in the top N. Sections are sent whole; a very large section is not trimmed yet.
- Milestone 9: `Hit` now carries `section_id`, `summary` and `keywords`; chunks loaded for a section have similarity 0. `strip_json_fence` moved from the enricher to `llm/client.py` because the selector needs it too.
- Milestone 9: tests: conftest makes the rewriter's and selector's model calls fail by default, so every test without its own fake exercises the fallback.
- Milestone 10: `/api/chat` streams `sources`, `text` pieces, then `done` (or `error`). Data is JSON so line breaks in the text are safe. The retrieval (B0-B7) runs before the response starts, so a failure there (the rewrite, selection and rerank already fall back) is still a plain HTTP 502 and the `error` event is for failures while the answer streams. Rejected: running everything inside the stream, because the database session is closed when the endpoint returns.
- Milestone 10: the streamed text is not cleaned on the server (the full answer is not known yet). Unknown ids stay in the text and the browser draws no tag for them; the ids are removed from the history that goes back to the server. `answer_question` (complete answer, ids cleaned) stays for the evaluation. The browser hides a tag that is still arriving (`[c1`) until its bracket closes.
- Milestone 10: on an `error` event the half-written answer is replaced by the error message, and that turn is left out of the history sent next time. Retries (`LLM_MAX_RETRIES`) only cover the start of the stream; a failure halfway is not retried.
- Milestone 10: the API sends `X-Accel-Buffering: no` as well as nginx's `proxy_buffering off` for `/api/chat`. The smoke test now reads the stream and fails if the text events arrive in fewer than 2 pieces or all within 0.05 s (a sign nginx buffers). Not yet run end to end: port 8080 was in use by a running copy of the app, which I left alone.
- Milestone 11: `sha256` stays unique, so an overwrite cannot insert the new row under the real hash while the old one exists. The new document is stored as `<sha256>:pending:<id>`; when its pipeline finishes, one transaction deletes the document that holds the real hash and gives the new one that hash. A failed overwrite leaves the old document alone and the new row shows as failed (the user can delete it). Rejected: dropping the unique constraint (the database would then allow duplicates) and a `replaces_id` column (needs a schema change, and there are no migrations). The old PDF file is removed after the commit.
- Milestone 11: when the same hash is in the request twice, or a 409 repeats on the `overwrite=true` resend, the page shows the api message instead of asking again. With several files in one request, one duplicate puts the whole request in the dialog (the api rejects the request as a whole); Overwrite resends all of them.
- Milestone 11: nginx's 413 page is not JSON, so the client maps 413 and 415 to fixed messages. The progress bar stays empty until `chunk_count` is known (the document is still being parsed and split).
- Milestone 12: `GET /api/documents` now also returns `section_count` (the design's documents table needs it and no field held it); it is counted with one grouped query, not stored on the row. The two new endpoints live in `api/sections.py` (not `documents.py`) because `/api/sections/{id}/chunks` is not under `/api/documents`.
- Milestone 12: the sections endpoint returns a flat list in document order with `level` and `parent_id`; sections are stored parents-first, so the browser draws the tree by indenting by `level` and needs no tree-building code. Each section carries its `chunk_count`. The chunks endpoint sends `has_embedding` instead of the vector.
- Milestone 12: the Database page shows all three levels at once on one page (documents, then the sections of the chosen document, then the chunks of the chosen section), so the numbers can be compared with the Upload page without navigating back. Choosing another document clears the chunks of the old one.
- Milestone 13: the README gives a decisions table (choice, rejected option, why) as a summary of this log, not a copy; this file stays the full record. It states plainly that retrieval and answers have not been measured, and that `SIMILARITY_CUTOFF` and `RERANK_MIN_SCORE` are provisional.
- Milestone 13: `scripts/smoke_test.sh` now copies `env/.env.template` and fills in the key, the same steps as the README, so a broken template or README step fails the test.
- Milestone 14 (harness): `Trace` now also keeps `cosine_scores` (one per candidate) and `rerank_scores` (one per reranked chunk), the only change to app code. The evaluation recomputes the thresholds from these stored scores instead of re-running the retrieval for every setting.
- Milestone 14: gold is the **full heading path** (`2 Scope > 2.1 Data`), as exported to `eval/trees/<pdf>.txt`, not the bare heading name. Bare names repeat across chapters ("Definitions"), paths do not, and a path is what `sections.heading_path` stores, so the overlap rule is a plain prefix check. Gold headings that are not in the ingested tree are rejected when the run starts.
- Milestone 14: two runs. `run.py --scores-only` runs once at the loosest grid settings (lowest cutoff, no rerank minimum, no selection call) and stores every candidate's scores; `report.py tune` picks thresholds leave-one-PDF-out from them; `run.py --folds` then runs the full pipeline once per question with the thresholds tuned without that question's PDF. This makes the headline (final context, with section selection) cross-validated without a selection call per grid point. Rejected: running the selection call for every setting of the grid (about 60 settings x 120 questions of Sonnet calls).
- Milestone 14: the tuning scores the **rerank stage** (top N, no selection), because the selection step is an LLM call and cannot be recomputed from stored scores. The pick is the middle (per parameter, lower middle) of the settings within `EVAL_TUNE_TOLERANCE` (1% of the questions) of the best accuracy, not the single best value. Grids and the tolerance are settings (`EVAL_*`).
- Milestone 14: unlike in the app, the eval stops when the reranker cannot load, and `run.py` exits non-zero and lists the questions where the rewrite, rerank or selection fell back (counted from the errors the retrieval logs; a follow-up that came back unchanged also counts). The app's fallbacks are right for users and wrong for measuring: they would silently make the numbers describe a different pipeline. The results table also stores a `fallback` flag per question.
- Milestone 14: the eval scripts refuse to run unless `DATABASE_URL` points at `EVAL_DATABASE` (`docchat_eval`), so a mistaken run cannot ingest the eval PDFs into the app database. Eval tables are in the `eval` schema; the unit tests drop the schema name to run on SQLite.
- Milestone 14: syncing the question files into the database keeps earlier runs' results (questions are merged, not recreated). Editing a question means running all runs that should be compared again.
- Milestone 14: PyYAML is now a direct dependency (the question files). It was already in the lockfile through another package.
- Milestone 14 (open): `evaluation-metrics.md` says the rewrite and selection calls run at temperature 0, but `llm/client.py` sets no temperature, so they use the API default and two runs can differ slightly. Not changed in this milestone (it touches app code outside the trace); needs a decision. Until then compare configurations with the sign test only when the flips are clearly lopsided.

## What broke

- Milestone 1: the stock Python `.gitignore` had `env/` and `ENV/` (virtualenv folders). Git on macOS matches case-insensitively, so both hid our `env/` config folder. Replaced with `env/.env`.
- Milestone 1: the memory warning fired on Docker set to 8 GB because the VM reports about 7.7 GB. `MIN_MEMORY_GB` default is 7.5.
- Milestone 1: uvicorn in the container could not import `env.config`; pytest's `pythonpath` setting does not apply to uvicorn. Fixed with `PYTHONPATH` in the Dockerfile.
- Milestone 2: the Python `lib/` rule in `.gitignore` also hid `frontend/src/lib`. Scoped it to `/backend/lib/`. `node_modules/` was not ignored yet.
- Milestone 4, on a 6-page paper: headings and page ranges match the table of contents. The running page header ("NOVA SBE") was detected as a heading and became the first section, with the title text under it. Page headers and footers that PyMuPDF4LLM turns into headings are not filtered out yet.
- Milestone 6: my first wait for the image build never ended, because `pgrep -f` matched the waiting command itself. Not a project bug; wait on the build process by its job instead.
- Milestone 13: `env/.env.template` was in the design and in the README steps but had never been committed, so `cp env/.env.template env/.env` would have failed on a fresh clone. The smoke test did not notice because it wrote `env/.env` directly. Added the template and changed the smoke test to copy it.
